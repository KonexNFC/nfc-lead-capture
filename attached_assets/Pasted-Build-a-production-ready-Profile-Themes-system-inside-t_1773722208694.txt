Build a production-ready “Profile Themes” system inside the Konex admin dashboard and public profile renderer.

PRODUCT CONTEXT
Konex is an NFC-powered digital profile platform. Users have public-facing profiles containing their identity, business info, social links, CTAs, media, booking/payment/review links, and other profile blocks. We want to introduce a multi-theme profile option so users can choose their own visual style without changing the underlying profile data structure.

CORE OBJECTIVE
Create a scalable theme engine where:
1. Each user keeps one profile data model
2. Users can select from multiple curated visual themes
3. Themes only affect presentation, not the actual profile content schema
4. Changes can be previewed live before publishing
5. Theme availability can be controlled by plan/tier
6. The implementation is clean, modular, and easy to extend later

SUCCESS CRITERIA
- Users can choose a theme from an “Appearance” or “Themes” section in dashboard
- Users can preview themes instantly on desktop and mobile views
- Users can save draft theme changes before publishing
- Public profile renders correctly with selected theme
- Existing profiles continue to work with a default theme fallback
- Theme system supports future premium upsells
- Admin can add new themes later without rewriting profile logic

TECHNICAL ARCHITECTURE
Implement this using:
1. One shared profile data schema
2. A theme configuration system using JSON or TypeScript objects
3. Design tokens per theme:
   - colors
   - typography
   - spacing
   - border radius
   - button style
   - shadows
   - section density
   - card/surface style
4. Shared reusable UI components that consume theme tokens
5. Theme-aware public profile renderer
6. Plan-based theme gating
7. Safe fallback handling if theme is missing or invalid

DO NOT build fully freeform drag-and-drop design customization.
DO build curated theme templates with controlled customization.

DATA MODEL / STORAGE
Add theme-related fields to the user profile settings:
- selectedThemeId
- themeVariant
- themeCustomizations
- themeDraft (optional)
- themePublishedAt (optional)

Suggested example:
{
  "selectedThemeId": "luxury_black",
  "themeVariant": "default",
  "themeCustomizations": {
    "accentColor": "#D4AF37",
    "buttonStyle": "filled"
  }
}

THEME CONFIG STRUCTURE
Create a central theme registry, for example:
- /lib/themes/
- /config/themes/
- /src/themes/

Each theme should define:
- id
- name
- description
- availability: free/pro/enterprise
- preview thumbnail metadata
- token values
- layout preferences
- supported customization options

Example shape:
{
  id: "luxury_black",
  name: "Luxury Black",
  description: "Dark, premium and refined",
  availability: "pro",
  supports: {
    accentColor: true,
    buttonStyle: false,
    darkLightToggle: false
  },
  tokens: {
    background: "#0B0B0B",
    surface: "#141414",
    textPrimary: "#FFFFFF",
    textSecondary: "#B5B5B5",
    accent: "#D4AF37",
    borderRadius: "16px",
    shadow: "soft",
    fontHeading: "serif-premium",
    fontBody: "sans-clean",
    spacing: "comfortable"
  },
  layout: {
    headerStyle: "centered",
    ctaStyle: "stacked",
    cardStyle: "elevated",
    sectionDivider: "subtle"
  }
}

- loading preview
- save failed

ACCESSIBILITY

- Keyboard accessibility in dashboard
- Theme previews should not rely on color alone
- Public profile must remain readable under all themes

PERFORMANCE

- Avoid duplicating profile rendering logic per theme
- Use one renderer with theme tokens rather than separate hardcoded templates where possible
- Lazy load heavy preview assets if needed
